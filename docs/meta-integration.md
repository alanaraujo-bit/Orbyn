## What publication does not buy you

The API-Setup page, step 5, is explicit: *"Para que seu app acesse dados ao
vivo, o Instagram exige que o processo de análise do app seja realizado. Passe
por esse processo para ter acesso avançado às permissões do Instagram."*

That is what the panel says. What the wire says is narrower, and it was
measured on 2026-08-30 at 23:53: a DM from account `<conta-de-terceiro>` — no role
on the app, unrelated to the operator — was delivered to the public webhook with
a valid signature and processed. **Receiving from strangers works at Standard Access; sending to them is
untested.** The funnel then ignored it as `unmatched_sender`, which is correct:
Orbyn answers leads it prospected, not whoever writes in. Note what that
implies about the evidence: the delivery exercised the webhook receiver and the
HMAC path only. No conversation was opened, no 24h window started, and
`instagram_business_manage_messages` was never called. Standard Access could
still gate the send side.

So App Review is not what stands between this app and receiving real traffic.
The claim that it is came from reading the panel instead of testing the path.
What has still never been exercised is an API **send** to an account without a
role; every successful send so far had one.

## Which secret signs the webhook

The signature is computed with the **Instagram app secret** of `Orbyn-IG`, shown
under "Chave secreta do app do Instagram" on the API setup page — not the Meta
app secret from Basic Settings. They are different values, and using the wrong
one produces a permanent 401 on every delivery.

## Defects found and fixed

Probing the live send endpoint with an invalid recipient returned:

```
400 IGApiException / code 100 / subcode 2534014
"Não foi possível encontrar o usuário solicitado."
```

Orbyn classified that as `api_unavailable` and counted it against the
`instagram_api` circuit breaker. That is wrong and would have hurt in
production: a handful of stale IGSIDs — leads who deleted or renamed their
account — would have opened the breaker and stopped **all** API messaging.

`classifyGraphError` now separates the cases:

| Condition | Mapped code | Retryable | Counts as outage |
| --- | --- | --- | --- |
| subcode 2534014 / 2534001 / 2018001 | `api_ineligible_recipient` | no | no |
| subcode 2534022 / 2018278 | `api_window_closed` | no | no |
| code 4 / 17 / 32 / 613 / 80007, or HTTP 429 | `rate_limit_exceeded` | yes | no |
| code 190 / 102 / 463 / 467 (dead token) | `api_unavailable` | no | **yes** |
| HTTP 5xx | `api_unavailable` | yes | **yes** |
| other 4xx | `api_unavailable` | no | no |

Verified against the live API: four consecutive invalid recipients left the
breaker closed and its failure count at zero. Covered by
`tests/integrations/graph-errors.test.ts`.

### 2. A failed API reply was never retried

The live handoff exposed a worse one. `deliverApiReply` wrote the outbound row
*before* the request — correct, since a crash between the two must not
double-send — but then treated the row's existence as proof of delivery. So a
transient failure (5xx, timeout, throttle) left a row behind, and the retry saw
a "duplicate" and returned **without sending**. The lead would never receive the
reply while the CRM showed it as sent.

Delivery is now anchored on the provider's message id: a row without one is an
attempt of unknown outcome and gets retried; a row with one is never sent again.
Covered by `tests/conversations/delivery-retry.test.ts`.

### 3. Every real inbound message was silently discarded

Meta's own test payload exposed the worst defect of the session. Instagram
delivers message events in two different envelopes:

```
entry[].messaging[]                    <- what Orbyn read
entry[].changes[] { field, value }     <- what Meta actually sends
```

The schema accepted both (each is optional), so a real delivery returned **HTTP
200 while extracting zero messages**. In production this would have meant every
lead reply vanishing without a trace and without an error — the funnel would
appear healthy and never advance past "abordado".

Both envelopes are now read, deduped by message id, with the timestamp
normalised (one envelope sends epoch milliseconds, the other a seconds string —
reading it raw dated messages to 1970). Covered by
`tests/integrations/webhook.test.ts`, using the exact payload Meta sent.

### 4. A mixed delivery was rejected wholesale

Meta batches event types: a text message can arrive alongside a read receipt, a
reaction or a seen marker. Read receipts carry no `sender` or `recipient`, but
the schema required both on every event — so **one unreadable sibling failed the
entire delivery with a 400**, taking any real message down with it, forever, on
every retry.

The receiver is now liberal in what it accepts and strict only about what it
uses: unknown or partial events parse and are skipped, real messages are
extracted. Schema rejections now log the payload's key structure (never its
contents) and raise a `webhook_payload_unreadable` alert — the previous log
said only "rejected", which cost an extra diagnostic round.

### 5. A delivered DM could vanish from the database

The first real send exposed a consistency bug. `sendFirstContact` performed the
real send and then did all its bookkeeping inside one transaction. The lead had
been closed by qualification, so the transition to `contacted` threw — and the
whole transaction rolled back, **including the record of a message already
sitting in the recipient's inbox**. The system believed nothing had been sent,
so a retry would have delivered a second real message to a real person.

Persistence of a completed send is now committed on its own, immediately after
the provider accepts it, along with the pacing counter. State transitions run
afterwards and are best-effort: a failure raises a `post_send_state_mismatch`
alert instead of erasing history. Covered by
`tests/campaigns/post-send-durability.test.ts`.

## Development mode does not deliver `messages` — proven

The decisive experiment, 2026-08-30. The operator sent four real messages from
their personal account (@alanarauj0__) to the business account (@aionixdev).

| Observation | Result |
| --- | --- |
| Messages arrived at @aionixdev | yes — "4 new messages", unread, visible in the inbox |
| `messages` webhooks delivered | **zero**, over more than seven minutes |
| Webhooks that did arrive | only `read` receipts, generated by @aionixdev — the account that *is* a tester |
| App mode | Development |

The pattern is consistent: Meta delivers events originating from accounts that
hold a role on the app, and silently drops events from everyone else while the
app is unpublished. The console warning — *"Seu app deve estar com o status de
publicado para receber webhooks"* — is literal.

This makes publishing a hard requirement for the inbound half, not an
optimisation. A real lead will never be a tester.

## Operational caveat: the tunnel URL is ephemeral

The webhook callback currently points at a free `trycloudflare.com` hostname,
which changes every time the tunnel restarts. After a restart the URL saved at
Meta is stale and deliveries go nowhere, silently. For sustained operation, use
a named Cloudflare tunnel or any stable hostname, and re-save the callback URL
whenever it changes.

## Security incident, 2026-08-30

While driving the official token generator, the flow forced re-authentication
and Chrome autofilled the password field. The orchestration tool captured the
accessibility snapshot of that page, which echoes input **values**, and printed
it. The redaction in place only matched token-shaped strings; a password has no
recognisable shape.

Fixed by adding a structural first pass that blanks the value of any input whose
accessible name matches senha/password/código/token/chave/secret/pin/cvv, before
any pattern matching runs. Captured artifacts were deleted. **The operator was
told to rotate the Instagram password**, since the value had already reached the
session transcript.

The access token pasted into the chat by the operator is likewise in that
transcript. It can be regenerated at any time from the same panel, which
invalidates the old one.
